## GitHub Secrets

`VPS_SSH_HOST` и `VPS_SSH_PASSWORD` обновлены для нового сервера; `VPS_SSH_USER=root` остаётся действующим. В `VPS_SSH_KNOWN_HOSTS` сохранён ED25519 host key, полученный при первом SSH-подключении и сверенный с ключом из установленной SSH-сессии. Это фиксация ключа первого подключения, а не независимая проверка через консоль провайдера.

Старые SSH-реквизиты сохранены отдельно в `LEGACY_CLOUD4BOX_SSH_HOST` и `LEGACY_CLOUD4BOX_SSH_PASSWORD`. Существующие `VPS_DOMAIN` и `VPS_CONSOLE_URL` относятся к Cloud4box. Для нового deploy workflow сохранён `REG_VPS_DOMAIN=snowbrick.ru`.

Пользователь изменил A-записи `snowbrick.ru` и `www.snowbrick.ru` на `194.58.102.218` в личном кабинете Рег.ру. Домен обслуживают `ns1.reg.ru` и `ns2.reg.ru`. Проверка Google DNS и Cloudflare DNS через HTTPS в 21:10–21:11 МСК 17.09.2026 подтвердила новый IP для обоих имён. Локальные DNS-запросы в тот же момент возвращали старый `194.58.112.174`; кэши и DNS-маршрут локального VPN могут давать отличающиеся результаты.

Отдельная DNS-панель `dnsadmin.hosting.reg.ru` из письма ранее отклоняла вход, но она не нужна для текущей зоны на `ns1.reg.ru` / `ns2.reg.ru`. Исправление её пароля не является условием запуска этого домена. DNS-пароль не сохранён как действующий секрет.

Прямые HTTP/HTTPS-запросы с именем `snowbrick.ru` на новый IP в 21:10 МСК не дали рабочего сайта: HTTP — пустой ответ, TLS — ошибка рукопожатия. Поэтому DNS уже подтверждён внешними резолверами, а публикация приложения ещё не завершена. Подробности — [DEPLOYMENT.md](DEPLOYMENT.md).

## Приложение и данные

Репозиторий: https://github.com/nicemoment777-code/amo, ветка `main`. Node.js 24, внешних npm-зависимостей нет. Команды: `node --test`, `npm start`. Локальный адрес — `http://127.0.0.1:3080`.

На исходном компьютере сохранены 20 заказов; они ранее успешно обновлялись через API. Ключи СДЭК находятся в `AMO_ACCOUNT_ID` и `AMO_PASSWORD`; номера выборки — в `CDEK_ORDER_NUMBERS`. Данные получателей не входят в Git и не должны попадать в публичные artifacts.

Известные номера обновляются при запуске и каждые 15 минут; очередь сохраняется, ошибки повторяются раз в минуту. История кабинета сохраняется в `cabinetSnapshot`. Общего метода перечисления всего исторического архива в используемом API нет. Webhook `ORDER_STATUS` позволяет узнавать новые номера, после чего карточка читается через API.

## Продолжение работы

1. При изменении реквизитов повторять GitHub Actions `Production preflight`: текущая проверка уже успешна; она не развёртывает приложение.
2. Перед развёртыванием повторно проверить DNS `snowbrick.ru` с GitHub runner: записи уже обновлены и `REG_VPS_DOMAIN` сохранён. Проверить также AAAA и CAA перед выпуском сертификата.
3. Проверить сценарий переноса в `ops/provision-server.sh`, данные и существующие подписки СДЭК, затем запустить `Deploy production` вручную.
4. Проверить HTTPS для `snowbrick.ru`, отказ без авторизации, загрузку заказов и получение реального webhook на новом адресе. Для `www.snowbrick.ru` отдельно добавить сертификат и настройку Nginx/перенаправление: текущий скрипт получает один домен.
5. Настроить резервные копии и отдельный SSH-доступ для развёртывания.

`Deploy production` и восстановление старого сервера запускаются только вручную. Обычный push обновляет код и запускает проверки; сам по себе он не устанавливает приложение на VPS.
